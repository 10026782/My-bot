## Unreleased

- **BUG-PENDING-APPROVAL-B (PR #311, #312, #313, #314): pending lead-approval "context poisoning" — fixed and verified in production end-to-end.** An unrelated message arriving between a lead-write preview and the user's "כן" could let that confirmation silently approve the older, now-stale action instead of the one the user actually meant. Closed across four PRs, each merged only after live production testing exposed the next gap in the previous fix:
  - **PR #311**: `ActionContract` gained `context_interrupted`/`reconfirmation_required`; `route_confirmation_word()`'s single-live-contract branch re-shows a readable business description and requires an explicit second "כן" instead of executing directly once an intervening message arrived.
  - **PR #312**: production testing showed the interrupt-marking hook lived only inside `run_agent()`, missing every message handled by a different code path (slash commands, callback buttons, wizard text/file capture, general media, Decision Hub attachment references). Replaced with a single global ingress-context gate applied once per inbound webhook event on both channels (Telegram, WhatsApp Twilio, WhatsApp Meta), after auth/dedup/identity resolution, before any routing. `ActionGateway.is_own_resolution_event()` reuses the real confirm/cancel/disambiguation routing logic to decide the one exemption, so it can't drift from actual behavior. Fail-closed: a marking failure is tagged `context_integrity_unknown` (never silently treated as "context intact").
  - **PR #313**: production testing then showed the legitimate second "כן" (the actual reconfirmation) was rejected by `guards.idempotency` as a duplicate of the first "כן" — the Telegram webhook's dedup key was the raw message text, so two distinct messages with identical text collided. Fixed to key on the provider's own event identity (`update_id:message_id`) instead; WhatsApp's two call sites already used a true unique id and were unaffected.
  - **PR #314**: production testing then showed that after the first reconfirmation prompt was shown once, a *second* intervening action didn't re-arm anything — the next "כן" executed the old contract directly. The boolean design only distinguished "interrupted vs not" and permanently disabled the check once `reconfirmation_required` latched. Replaced with a bounded one-shot FSM: a second interruption after the prompt was already shown supersedes the contract outright (terminal, not re-armed), with a specific "your previous action was superseded, resubmit" message instead of a silent dead end. Separately, `compose_status_reply()`'s execution receipt now reuses the frozen contract's business description instead of showing the bare tool name.
  - **Final verification (12/07/2026)**: a full verbatim production transcript matches the designed behavior exactly across the whole chain — preview, two interruptions, first "כן" (exact reconfirmation wording), a third interruption after the prompt was shown, second "כן" (exact supersede wording), no execution. See `BUG_AUDIT_LOG.md`'s BUG-108/BUG-PENDING-APPROVAL-B entry and its three Follow-ups for full detail.

- **BUG-081 (C101, PR #259/#260/#261): Business Memory `Domain` written to its own field, not overloaded into `Tags`**: `BusinessMemoryFields` had no dedicated `Domain` field (unlike every other table in the schema), so `cmd_update.py`/`media_handler.py` wrote the raw internal domain key (e.g. `"media"`) directly into the generic `Tags` `multipleSelects` field with no guarantee it was an already-defined option — Airtable rejects unknown select options with a 422 (no `typecast=true` in the gateway). Added `BusinessMemoryFields.DOMAIN` and `cmd_update.normalize_business_memory_fields()`, called from both write sites: maps the domain key to a confirmed live `Domain` option and filters `Tags` down to actual valid options. A first-pass mapping sent `"real_estate"` (lowercase) to the `Domain` field — confirmed via live production evidence to be stale (Airtable had 2 duplicate real-estate options; the lowercase one was removed, leaving only Title Case `"Real Estate"`) — fixed in a follow-up commit. A second live 422 then surfaced: `_VALID_TAGS` still listed lowercase `"real_estate"` as a valid standalone tag, so it kept reaching Airtable via `Tags` even after the `Domain` fix; removing it first produced an empty `Tags` instead of the correct value, so a `_TAG_NORMALIZE` map was added to canonicalize it to `"Real Estate"` before filtering. Final behavior for `domain="real_estate"`: `Domain="Real Estate"` and `Tags=["Real Estate"]`, no lowercase value reaches Airtable anywhere. **Known follow-up, not yet built**: `weekly_summary.py::_group_by_domain()` and `tma_api.py`'s Business Memory listing still read `Tags[0]` as the domain and will silently default once new records carry `Domain` instead — deferred, piggybacked on either feature's activation (`FEATURE_WEEKLY_SUMMARY` off, TMA business memory screen not in active use).
- **BUG-080 (C100, PR #258): Date-only Airtable fields no longer sent full datetime strings**: `BusinessMemoryFields.DATE`, `DecisionEventFields.EVENT_DATE`, and `DecisionInboxFields.RECEIVED` are plain `Date` fields in Airtable (confirmed against live field-type metadata across all 4 Decision Hub tables), but all 7 manual write sites (`cmd_update.py`, `media_handler.py`, `cmd_decision.py` ×5) sent a full `datetime.now(...).isoformat()` string (time + microseconds + UTC offset) — rejected with a 422 (no `typecast=true` in the gateway). Changed to `.date().isoformat()` at all 7 sites; two `FileUploadResult(timestamp=...)` sites (an in-memory `session_store` object, not an Airtable field) and one read-only sort-key usage were deliberately left unchanged.
- **C99 (PR #257): extract document text into `/update` Business Memory entries**: photo/document attachments captured mid-`/update` (see BUG-078 below) were only saved with their caption and Drive link — the document's content itself was never read. Added `media_handler.extract_text_if_document(file_bytes, mime_type)`, wrapping the existing `document_converter.convert_document()` (handles temp-file writing/cleanup and unsupported-format/conversion-failure fallback to `None` internally); `capture_photo_or_document` now folds the extracted text into the saved entry alongside the caption and Drive link.
- **BUG-079 (C98, PR #256): `/update`'s free-text step now reaches `capture_text` instead of leaking into `run_agent`**: `app.py`'s webhook only called `bot.process_new_updates()` (the only thing that dispatches `@bot.message_handler`-registered handlers, including `cmd_update.py`'s `capture_text`) for slash-command text — plain free text sent during `/update`'s final step fell through to `idempotency.is_duplicate()` and then the general `run_agent()` pipeline instead, silently abandoning the pending wizard state until its 30-minute TTL expired. This had been broken since `cmd_update.py` (C20) was first added — the wizard's primary use case, not an edge case. Added `cmd_update.has_pending_text_capture()`, checked right after the slash-command branch and before the idempotency check (fail-open on error); when a session is waiting on its text step, the webhook now dispatches through `bot.process_new_updates()` itself.
- **BUG-078 (C97, PR #255): `/update` now claims a photo/document attachment instead of losing it**: `app.py`'s webhook routed `photo`/`document` updates straight to the generic Drive-upload handler (`_handle_telegram_media`) before ever calling `bot.process_new_updates()`, so an attachment sent while an `/update` session was waiting on its free-text step fell through to the generic upload flow — losing the chosen domain/entry_type and orphaning the pending wizard state until its TTL expired. Added `cmd_update.has_pending_file_capture()`/`capture_photo_or_document()`, checked in `app.py` before the generic media handler for `photo`/`document` content types; the file is uploaded via the existing `media_handler` pipeline (best-effort) and saved to Business Memory with the domain/entry_type already selected in the wizard.

- **C94: added `FEATURE_INGRESS_ENVELOPE` kill-switch**: C94 (below) shipped across 4 merged PRs with no feature flag at all.
