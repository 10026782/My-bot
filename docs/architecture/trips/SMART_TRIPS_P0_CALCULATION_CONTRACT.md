## 1. היקף P0

מסך אחד, טאב אחד: **השוואת הצעות**. נסיעה חד-כיוונית של נוסע, 2–5 הצעות בתשלום. נקודת התחלה ונקודת סיום זהות לכל ההצעות. המתכנן הרב-עצירתי (P1) לא נכלל כאן.

## 2. יחידות וכללים כלליים

- סכומים בש"ח, מרחק בק"מ, זמן בדקות, אזור זמן `Asia/Jerusalem`.
- החישוב ב-`Decimal`. עיגול ל-0.01 ש"ח ולדקה שלמה **רק בפלט**.
- ערך חסר או לא תקין ⇒ התוצאה מסומנת `incomplete` עם `warnings` מפורשים. **אין ערכי ברירת מחדל ממוצאים** (למעט p_return=0, ראו §3).
- סכום ההסתברויות תמיד 100%: p להצלחה, 1−p לכישלון. p חייב להיות בטווח [0,1].
- "הרווח" = **תרומה** (הכנסה פחות עלויות נסיעה). אין מס, אין מע"מ, ולא מוצג כרווח נטו לכיס. תווית קבועה בממשק: "לפני מס".

- `return` חסר או `probability` חסר ⇒ **p=0, חזרה ריקה** (ברירת מחדל שמרנית, מוצגת בהנחות).

**תקרות ולידציה** (חריגה ⇒ 400 עם שם השדה בלבד): fuel 1–30, km_per_l 1–50, wear 0–10, fee 0–100, fare 0–5000, service 0–240, wait 0–720, km לרגל ≤ 1000, minutes לרגל ≤ 1440, offers 2–5. גוף הבקשה ≤ 64KB.

## 4. מודל חישוב לכל הצעה

### 4.1 רגליים

| רגל | מ → אל | טעונה? | זמן יציאה |
|---|---|---|---|
| L1 | origin → pickup | ריקה | `departure_at` |
| L2 | pickup → dropoff | טעונה | סוף L1 + שירות איסוף |
| L3f (כישלון) | dropoff → final | ריקה | סוף L2 + שירות פריקה + `wait_failure` |
| L3s (הצלחה): חזרה | dropoff → return.pickup | ריקה | סוף L2 + שירות פריקה + `wait_success` |
| L4s | return.pickup → return.destination | טעונה | סוף L3s |
| L5s | return.destination → final | ריקה | סוף L4s |

רגל שנקודות המוצא והיעד שלה זהות לא נשלחת לספק: `km=0, minutes=0`. כל רגל מחושבת בשעת היציאה המנובאת שלה. **אין הכפלת ETA של ההלוך**.

### 4.2 תרחישים

- **empty** (p<1): L1, L2, L3f; הכנסה = `outbound_fare`; המתנה = `wait_failure`.
- **return** (p>0): L1, L2, L3s, L4s, L5s; הכנסה = `outbound_fare + return.fare`; המתנה = `wait_success`.
- חזרה **מאושרת** = `p=1` (תרחיש return בלבד). הממשק מבדיל "מאושרת" מ"משוערת" לפי סימון המשתמש.

### 4.3 נוסחאות (לכל תרחיש s)

```
FuelCost_leg   = km / km_per_l * fuel_price
WearCost_leg   = km * wear_ils_per_km
Revenue_s      = Σ fares של התרחיש
Fees_s         = Revenue_s * platform_fee_pct / 100
Costs_s        = Σ_legs (FuelCost + WearCost) + fixed_cost + extra_costs
Contribution_s = Revenue_s − Fees_s − Costs_s                 (כלכלית, כולל שחיקה)
CashContrib_s  = Contribution_s + Σ_legs WearCost             (במזומן, אחרי דלק בלבד)
Time_s         = Σ_legs minutes + service_minutes (איסוף + פריקה, פעם אחת כל אחד) + wait_s
Deadhead_km_s  = Σ km של רגליים ריקות
PerHour_s      = Contribution_s / (Time_s / 60)               ; Time_s ≤ 0 ⇒ invalid
```

`service_minutes` הוא סכום איסוף+פריקה כפי שהוזן (שדה אחד), נספר פעם אחת.

### 4.4 תוחלת (שתי מדדים נפרדים ומתויגים)

```
E[Contribution] = Σ p_s * Contribution_s
E[Time]         = Σ p_s * Time_s
throughput      = E[Contribution] / (E[Time] / 60)       ← "תפוקה מתוכננת לשעה"  (מדד הדירוג)
E[PerHour]      = Σ p_s * PerHour_s                      ← "ממוצע שעתי לפי תרחישים" (מוצג בנפרד, מתויג)
downside        = התרחיש עם Contribution הנמוכה ביותר מבין p_s>0 (כולל PerHour שלו)
```

שני המדדים שונים. לא מחליפים ביניהם ולא ממזגים.

### 4.5 דירוג

`objective` קובע את סדר ההצגה; כל ההצעות מוצגות תמיד עם כל המדדים:

| objective | מיון (סדר יורד טוב→רע) |
|---|---|
| `throughput` (ברירת מחדל) | `throughput` ↓ |
| `contribution` | `E[Contribution]` ↓ |
| `earliest_arrival` | זמן הגעה צפוי ל-final ↑ (`departure_at + E[Time]`) |
| `least_deadhead` | `E[Deadhead_km]` ↑ |
| `downside` | `Contribution` של הדאונסייד ↓ |

הפלט כולל `explanation` בעברית: מה ניצח, ובאילו מדדים הוא מפסיד. **אין המלצה אטומה.** הצעה לא שלמה לא מדורגת, ומוצגת בנפרד.

## 5. החלטת "לחכות או לצאת"

לכל הצעה עם p>0:

```
V(x) = Contribution(x) − o * Time(x)/60            ; o = opportunity_cost_ils_per_h (קלט, ברירת מחדל 0)
V_leave  = V(תרחיש empty עם wait=0)                 (יוצא מיד, חוזר ריק)
V_fail   = V(תרחיש empty עם wait_failure)
V_succ   = V(תרחיש return עם wait_success)
V_wait(p) = p*V_succ + (1−p)*V_fail

p* (break-even) = (V_leave − V_fail) / (V_succ − V_fail)        ; אם V_succ ≤ V_fail: "לא כדאי לחכות לעולם"
p* ≤ 0  ⇒ "החכמה תמיד כדאית";  p* ≥ 1 ⇒ "לא כדאי לחכות לעולם"
R* (תשלום חזרה מינימלי ל-p נתון)  = ((V_leave − (1−p)*V_fail)/p − V_succ0) / (1 − fee)
   כאשר V_succ0 = V_succ כשתשלום החזרה = 0 ; p=0 ⇒ אין ערך
```

`o=0` ⇒ אזהרה קבועה: "ללא עלות הזדמנות, המתנה נראית חינמית." הערך o הוא קלט משתמש, לא נתון שוק.

## 6. מקור ה-ETA, ומה קורה בלי Google (תשובה לשאלה 4)

> **עודכן ב-A1:** שלושת המקורות שלהלן הם עכשיו שלושה מצבי `RouteProvider` (`LOCAL_ROUTE`, `TRAFFIC_AWARE`, `MANUAL`), ו-Google אינו ברירת מחדל. ראו §14.4. הטקסט המקורי נשמר להשוואה.

הרגליים מגיעות מאחד משלושה מקורות, ומסומנות בפלט (`provider` לכל רגל):

1. `google_routes`: ק"מ וזמן מ-Google בזמן היציאה המנובא, עם `computed_at`. `traffic_prediction_quality = "forecast"` לכל יציאה עתידית.
2. `manual`: המשתמש הקליד ק"מ ודקות לרגל (`manual_legs`). מסומן "קלט ידני" וללא תנועה.
3. `unavailable`: אין מפתח, תקציב נגמר או שגיאה, ואין קלט ידני לרגל ⇒ ההצעה `incomplete` עם "לא ניתן לחשב ETA חי". **לא ממציאים ערכים.**

כלומר "מצב בלי Maps" הוא מצב ידני: המסך עדיין עובד ומחשב, אבל המשתמש מזין ק"מ ודקות בעצמו וכל מספר מסומן כך. זו ברירת המחדל המוצעת כל עוד אין מפתח (השאלה הייתה: האם לאפשר זאת או לחסום לגמרי).

## 8. שמירת נתונים (תשובה לשאלה 3)

**המלצה: P0 לא שומר דבר בשרת ולא ב-Airtable.** פרופיל הרכב נשמר ב-Telegram CloudStorage של המשתמש עצמו (מפתח `trips.vehicle.v1`), עם fallback ל-`localStorage`.

נימוק: CloudStorage כבר מחובר לחשבון הטלגרם ועובד בין מכשירים, ולכן Airtable לא נותן תמורה נוספת ב-P0. Airtable מצריך טבלה חדשה, בדיקת סכימה לפי `AIRTABLE_SCHEMA_GOVERNANCE`, כתיבה דרך `airtable_gateway.py`, ומדיניות פרטיות על כתובות. נשקול אותו שוב ב-P1 **רק אם** תרצה היסטוריית נסיעות או "כמה הרווחתי בפועל".

אזהרה: הפרופיל נשלח בכל בקשה (הוא לא נשמר בשרת), ולכן אין צורך בטבלה כדי שהחישוב יעבוד.

## 9. גישה פתוחה: השלכות שחייבות החלטה

הבקשה "גישה פתוחה" משמעה כל משתמש TMA מאומת. זה שונה מדפוס ה-FCC (owner + canary). צריך לוודא ארבעה דברים לפני מימוש:

1. **עלות:** כל משתמש צורך מהתקציב המשותף. הצעה: תקציב שרת חודשי כולל 2,000 בקשות, ועוד מכסה לכל משתמש (למשל 150 בחודש), והודעת "המכסה נגמרה" במקום קריאה נוספת.
2. **תפקידים נמוכים:** `lead`/`guest`/`readonly` הם **לא** משתמשי TMA רגילים. הצעה: לפתוח ל-`owner`/`partner`/`manager`/`employee` בלבד (`Role.rank ≥ 3`). זו הצעה, לא נבדקה מול ההרשאות החיות.
3. **דגל:** `FEATURE_SMART_TRIPS` כבוי עד אישור, ללא רשימת canary אלא אם תבקש.
4. **הגנה:** `RateLimiter` הקיים הוא בזיכרון (אובד ב-restart), לכן תקציב הבקשות חייב להישמר בצורה עמידה. הצעה: מונה `usage_events` ב-PostgreSQL (קיים כבר), או לחלופין מונה בזיכרון עם תקרה שמרנית, והבחירה מסומנת פתוחה לאישורך.

## 10. תרחישי בדיקה חובה (golden)

הנתונים להלן **דוגמה להמחשה בלבד**, לא מחיר שוק. רכב: דלק 7.5, 12 ק"מ/ל, שחיקה 0.30, ללא עמלה/אגרות, `o=40`, כל הרגליים `manual`.
עלות לק"מ = 7.5/12 + 0.30 = **0.925 ש"ח**.

**הצעה A** (אשדוד): תשלום 230, שירות 15, L1 10ק"מ/15ד', L2 40/40, חזרה ריקה 40/40, p=0.30, תשלום חזרה 200, חזרה טעונה 40/40, המתנה הצלחה 40, כישלון 30.
**הצעה B** (ירושלים): תשלום 150, שירות 15, L1 10/15, L2 65/60, חזרה ריקה 65/60, p=0.50, תשלום חזרה 120, חזרה טעונה 65/60, המתנה הצלחה 25, כישלון 20.

| מדד | A | B |
|---|---|---|
| כישלון: תרומה / זמן / ק"מ | 146.75 / 140 / 90 | 20.50 / 170 / 140 |
| הצלחה: תרומה / זמן | 346.75 / 150 | 140.50 / 175 |
| E[Contribution] | 206.75 | 80.50 |
| E[Time] | 143.0 | 172.5 |
| **throughput** | **86.75** | **28.00** |
| E[PerHour] | 85.64 | 27.70 |

דגימת רגישות ל-A: p=0 → 62.89; 0.1 → 70.96; 0.2 → 78.91; 0.3 → 86.75; 0.5 → 102.10; 1.0 → 138.70.
החלטת המתנה ל-A (`o=40`): יציאה מיד: תרומה 146.75, זמן 110, `V_leave`=73.42; `V_fail`=53.42; `V_succ`=246.75; **p\* = 0.1034**; **R\* ב-p=0.30 = 73.33 ש"ח**.

(החישוב הותאם מול סקריפט ייחוס חיצוני, ולא הועתק לריפו. הבדיקות הרשמיות יחושבו בנפרד על קוד המימוש.)

**בדיקות נוספות:**
1. p=0, p=0.3, p=1 (A) ⇒ מתאים ל-§10.
2. כישלון חיפוש: זמן ההמתנה הכושלת נכלל בזמן ובדאונסייד.
3. הצלחה: כוללת המתנה, תשלום שני וחזרה אמיתית.
4. זמן כולל 0 או שלילי ⇒ `invalid`, ללא חלוקה באפס.
5. חזרה חלקית: `return.pickup`≠dropoff ו-`return.destination`≠final ⇒ L3s ו-L5s אינן אפס.
6. נקודות זהות (pickup=origin, או dropoff=final) ⇒ רגל אפס, ללא קריאת ספק.
7. תנועה: שני זמני יציאה שונים לאותה רגל ⇒ שתי בקשות ספק נפרדות; ETA ההלוך לא מוכפל.
8. p מחוץ ל-[0,1], fare שלילי, חסר origin/final ⇒ 400 או `incomplete`.
9. חסר מפתח ואין `manual_legs` ⇒ `incomplete` עם הודעה, ללא ערכים.
10. `o=0` ⇒ אזהרה.
11. בקשות ספק לא עולות על תקציב הבקשה; בקשה זהה באותה חישוב (אותה רגל ואותו חלון 5 דקות) נשלחת פעם אחת.
12. הפרדה בין מדד throughput ל-E[PerHour]: שני מספרים שונים בפלט.

## 11. עלות בקשות (תיקון לדוח הקודם)

לכל הצעה: **עד 6** רגליים נפרדות (לא 5). עם `return.pickup=dropoff` ו-`return.destination=final`: **4**, כי שתי רגלי dropoff→final יוצאות בשעות שונות. 5 הצעות במקרה הגרוע: 30 בקשות, כלומר ~$0.30 מעל מכסת החינם. שימוש ממוצע (3 הצעות × 4–5 רגליים × 3 השוואות ביום ≈ 1,350 בחודש) נשאר בתוך 5,000 החינמיות. עם גישה פתוחה, הצריכה מצטברת לכל המשתמשים, ולכן §9.1.

## 12. מוקאפ UI (טקסט)

### 14.4 עדכון הארכיטקטורה: `RouteProvider`

ממשק אחיד (Protocol) ב-`core/trips/route_provider.py`, וארבעה רכיבים סביבו:

```python
class RouteMode(str, Enum):
    LOCAL_ROUTE   = "LOCAL_ROUTE"     # OSRM עצמאי: ק"מ וזמן זרימה חופשית, ללא עלות לקריאה
    TRAFFIC_AWARE = "TRAFFIC_AWARE"   # Google Routes, רק לפי בקשה מפורשת, עם תקציב
    MANUAL        = "MANUAL"          # המשתמש מקליד km/דקות

class LegResult:    km; minutes; provider; time_basis; computed_at; status
class MatrixResult: km[][]; minutes[][]; status[][]   # status לכל תא: ok | no_route | unavailable

class RouteProvider(Protocol):
    mode: RouteMode
    def leg(self, a: Coord, b: Coord, depart_at: datetime) -> LegResult: ...
    def matrix(self, sources: list[Coord], targets: list[Coord], depart_at: datetime) -> MatrixResult: ...
    def health(self) -> ProviderHealth: ...
```

- **`time_basis`:** `free_flow` (מקומי), `traffic_forecast` (Google), `manual` (קלט משתמש). הפלט מציג אותו ליד כל רגל.
- **LOCAL_ROUTE:** `core/trips/providers/local_osrm.py`. קורא ל-OSRM דרך `httpx` ברשת הפנימית, timeout קצר (הצעה: 2 שניות), בלי retry אוטומטי לספק בתשלום.
- **TRAFFIC_AWARE:** `core/trips/providers/google_routes.py`. נקרא **רק** בלחיצה על "בדוק עם תנועה" (למועמדים המובילים, לא לכל ההצעות), עם תקציב ומכסה מ-§9.
- **MANUAL:** `core/trips/providers/manual.py`, זהה ל-§6 המקורי.
- **אין מעבר שקט לספק בתשלום:** אם `LOCAL_ROUTE` אינו זמין, התוצאה `incomplete` עם "ניתוב מקומי לא זמין", ורק המשתמש יכול לבחור TRAFFIC_AWARE או MANUAL. כך מובטח שגישה פתוחה לא מייצרת עלות בלתי מבוקרת.
- **בחירת ספק:** `core/trips/provider_factory.py` לפי `routing_mode` בבקשה ו-health. ברירת מחדל מוצעת: `LOCAL_ROUTE` כשהשירות מוגדר ובריא, אחרת `MANUAL`.

**מה לא משתנה:** כל החישובים ב-§4–5 הם פונקציות טהורות על רגליים (km, minutes). הן אינן יודעות מי הספק, כך שאותן בדיקות golden של §10 חלות על שלושת המצבים.

### 14.5 פענוח מיקומים (סעיף 4)

- אף אחד מהמנועים אינו geocoder. OSRM ו-Valhalla רק **מצמידים נקודה לכביש** (`nearest`/`locate`).
- הצעה: `core/trips/locator.py` עם ממשק `Locator.resolve(place) -> Coord | Ambiguous | NotFound`. מימוש ראשון: **`DictionaryLocator`** על המילון המאושר (רחוב / שכונה / צומת / עיר, עם קואורדינטה לכל ערך).
- אם למילון אין קואורדינטות: לבצע **פעם אחת, offline** והעברה לקובץ סטטי (לא geocoding בזמן ריצה). אפשרויות: Google Geocoding חד-פעמי (כמה מאות עד אלפי ערכים, בתוך 10,000 החינמיות) או Nominatim ציבורי רק לכמות קטנה (המדיניות הציבורית: עד בקשה אחת בשנייה, שימוש לא כבד).
- Geocoder עצמאי (Nominatim/Photon/Pelias): **נדחה** ל-P0. הוא שירות כבד נוסף (PostgreSQL/PostGIS או Elasticsearch), ואיכות מספרי הבתים של OSM בישראל לא נבדקה.
- טקסט חופשי שלא במילון ⇒ `Ambiguous`/`NotFound` עם הצעות מהמילון. אין ניחוש. Google Geocoding אפשרי רק כבחירה מפורשת, ולא כברירת מחדל.

### 14.6 טווח עיר יעד ללא כתובת הורדה (סעיף 5)

מצב: ההצעה מציינת רק "ירושלים" ולא כתובת. מה שמחושב:

1. מהמילון: קבוצת **K נקודות מייצגות** לעיר (שכונות/צמתים מרכזיים, עם משקל אם קיים), K≈10–30.
2. מטריצה אחת במנוע המקומי: `pickup → K נקודות` ו-`K נקודות → final`. עלות: ~2K תאים, אפס עלות כסף.
3. לכל נקודה מחושבת הצעה מלאה לפי §4, באותו זוג רגליים (אותה נקודה בהלוך ובחזרה), ואז:
   - **מינימום** = הנקודה הקרובה ביותר (הערך הנמוך ביותר, כולל הנקודה הזולה ביותר).
   - **טיפוסי** = חציון (או ממוצע משוקלל אם יש משקלים).
   - **מקסימום** = אחוזון 95 (ולא ערך קיצוני יחיד), כדי שנקודה חריגה אחת לא תשלוט. הערך הקיצוני המוחלט מוצג בנפרד אם נדרש.
4. תוצאה: `range` לכל מדד (ק"מ, דקות, תרומה, תפוקה), והדירוג המוצג משתמש ב-**טיפוסי**; ה-downside ב-**מקסימום**.
5. Google אינו מתאים לזה: 20 נקודות ×2 כיוונים הן ~40 תאי Matrix לכל הצעה, וזה הנימוק החזק ביותר ל-LOCAL_ROUTE.

אזהרות מחייבות בממשק: "הטווח מוערך לפי עיר ולא לפי כתובת", ו"נקודות הייצוג מהמילון".

### 14.7 ביצועים (סעיף 6) — יעדים, לא מדידות

- יעד: קריאת `POST /api/trips/compare` שלמה (5 הצעות, כל הרגליים, מטריצת טווח לעיר) **p95 ≤ 500ms** במצב LOCAL_ROUTE. זו הצעת יעד לאימות ב-spike, ואינה תוצאה.
- הערכת עבודה: ~30 רגליים + 2 מטריצות קטנות ל-K≤30. מטריצה בסדר גודל כזה נחשבת קלה ל-OSRM, אך לא נמדדה כאן.
- הגנה: `BoundedSemaphore` ו-`RateLimiter` כמו ב-`portfolio_lab_simulate`.
- לעומת זאת Google: כל רגל היא בקשת רשת נפרדת. לכן LOCAL_ROUTE משפר גם את הזמן, ולא רק את העלות.

### 14.8 דיוק מול Google (סעיף 8) — פרוטוקול מדידה, לא בוצע

- מדגם מוצע: **40 מסלולים** בישראל: ערים מרכזיות (תל אביב, ירושלים, חיפה, באר שבע, אשדוד, אילת), מסלולים קצרים בתוך עיר, בין-עירוניים ארוכים, ומסלולים עם כביש 6 וכבישי אגרה.
- השוואה: ק"מ ו-דקות מול Google `TRAFFIC_UNAWARE` (בסיס סטטי) ומול `TRAFFIC_AWARE` ב-3 שעות (בוקר, צהריים, ערב).
- קריטריוני קבלה מוצעים: חציון שגיאת מרחק ≤5%, אחוזון 90 ≤10%; חציון שגיאת זמן ≤10% מול `TRAFFIC_UNAWARE`. **ביחס ל-`TRAFFIC_AWARE` בשעות עומס מצופה תת-הערכה שיטתית** של הזמן המקומי, והמטרה היא לכמת אותה ולהחליט אם להוסיף מקדם עומס לפי שעה (קלט משתמש או מכויל), ולא להניח מראש.
- עלות הבדיקה: ~160 בקשות Google, בתוך המכסה החינמית.
- הערה ל-ODbL והדיוק: כבישים חסרים או תגיות מהירות שגויות ב-OSM הם סיכון הדיוק העיקרי, והמדגם צריך להכיל מסלולים כאלה.

### 14.9 רישיונות ותפעול (סעיף 7)

### 14.10 שינויים בחוזה `POST /api/trips/compare` (מינימליים)

| איפה | שינוי | תאימות לאחור |
|---|---|---|
| בקשה | שדה חדש `routing_mode`: `LOCAL_ROUTE` \| `TRAFFIC_AWARE` \| `MANUAL` (ברירת מחדל: לפי health, ראו §14.4) | תוספתי |
| `Place` | צורות חדשות: `{"dict_id": ".."}` ו-`{"city": ".."}` | תוספתי |
| `offer.dropoff` | מותר `{"city": ".."}`, ואז הפלט כולל `range` | תוספתי |
| פלט, רגל | `provider` מקבל `osrm`; שדה חדש `time_basis` | תוספתי |
| פלט, הצעה | שדה אופציונלי `range`: `{min, typical, max}` לכל מדד | תוספתי |
| `traffic_prediction_quality` | ערכים: `none` (מקומי), `forecast` (Google), `manual` | תוספתי |
| `provider.requests_used`, `budget_remaining` | מתייחסים ל-Google בלבד; במקומי `null` | תאימות |

כל הנוסחאות, הקלטים הכלכליים, ה-`ranking`, ה-`wait_decision` וה-`sensitivity` נשארים זהים.

### 14.11 בדיקות חדשות (נוספות ל-§10)

13. אותה כלכלה בכל ספק: אותן רגליים ⇒ אותן תוצאות ב-LOCAL, TRAFFIC ו-MANUAL.
14. `LOCAL_ROUTE` לא זמין ⇒ `incomplete` ולא מעבר שקט ל-Google.
15. `no_route` מהמנוע ⇒ הצעה `incomplete` ללא ערך.
16. טווח עיר: min ≤ typical ≤ max בכל מדד; K=1 ⇒ שלושתם שווים.
17. אותה נקודת ייצוג בהלוך ובחזרה ⇒ עקביות בין שתי הרגליים.
18. עיר ללא ערכים במילון ⇒ `NotFound`, ללא ניחוש.
19. `TRAFFIC_AWARE` נקרא רק בלחיצה מפורשת, ורק למועמדים שנבחרו.
20. תווית `time_basis` מופיעה ליד כל רגל, ואזהרת "ללא עומסים" בכל תוצאת LOCAL.

| שלב | תוכן | תלות | אומדן |

### 14.13 המלצה מנומקת

1. **לאמץ את הארכיטקטורה** `RouteProvider` עם שלושה מצבים. היא מפרידה את הכלכלה מהספק, ולכן אינה מסכנת את החישוב ומאפשרת להחליף מנוע אחר כך.
2. **OSRM כמנוע LOCAL_ROUTE** (מצב MLD): מטריצה מובנית, רישיון BSD-2, release חודשי, multi-arch. Valhalla כגיבוי עתידי. GraphHopper נדחה.
3. **לא לבנות geocoder עצמאי ב-P0.** להשתמש במילון המאושר כ-`DictionaryLocator`.
4. **הערכה כנה של הערך:** לפי הערכת הצריכה בדוח הראשון, Google כמעט לא עולה כסף (בתוך המכסה החינמית). הטיעונים החזקים בעד מקומי הם: (א) טווח עיר דורש עשרות תאי מטריצה לכל הצעה, (ב) אין תלות במכסה כשהגישה פתוחה לכל המשתמשים, (ג) זמן תגובה, (ד) עצמאות מספק. הטיעון "חיסכון כספי" חלש.
5. **המגבלה העיקרית:** זמן מקומי הוא זרימה חופשית. בשעות עומס הוא תת-אמוד, ועלול לשבש את דירוג ההצעות. לכן ההמלצה: ללא Google ברירת מחדל, אבל **כפתור "בדוק עם תנועה" לשתי ההצעות המובילות** ותווית ברורה. מדידה (G1) תקבע אם מקדם עומס לפי שעה מספיק.
6. **סדר:** לבנות קודם C1 (כלכלה + ממשק + MANUAL) ו-C2, כי אינם תלויים בתשתית. את C3 (OSRM) לבצע רק אחרי G1 ואחרי שיש מכונה (Oracle M1). לדחות: Nominatim/Photon, Valhalla, מקדמי עומס מכוילים.

### 14.14 החלטות בעלים נדרשות (מעבר ל-§13)

1. **המילון:** איפה הוא, באיזה פורמט, וכמה ערכים יש בו, והאם יש קואורדינטות? בלי זה אי אפשר לאפיין §14.5–14.6.
2. **איפה מריצים OSRM:** ב-Oracle (תלוי ב-M1 שטרם התחיל), במכונה נפרדת זולה, או לדחות `LOCAL_ROUTE` ולהתחיל עם Google+MANUAL.
3. **אישור spike (G1):** הרצה חד-פעמית של OSRM על מכונה זמנית והורדת מפת ישראל (115MB), וכ-160 בקשות Google, לצורך מדידה בלבד.
4. **ברירת מחדל מוצעת:** `LOCAL_ROUTE` כשבריא, אחרת `MANUAL` (ללא מעבר שקט ל-Google). לאשר או לשנות.
5. **הכרעה משפטית:** האם נדרשת בדיקה לפני שחרור בנוגע ל-ODbL ושימוש בתוצרים מחושבים.
