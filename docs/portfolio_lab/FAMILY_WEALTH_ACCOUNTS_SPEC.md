# SPEC — מודל חשבונות להון משפחתי (טיוטה לאישור בעלים)

תאריך: 14/10/2026 · סטטוס: **SPEC בלבד — לא אושר.** אין שינוי Airtable, אין קוד, אין PR מכוחו.
Planning Gate: **FULL** (persistence + authority + schema + multi-layer).

## 0. החלטת בעלים שמעדכנת את התכנון

אין בונים מעקב אחרי קרן אחת. ההון המשפחתי כולל כמה חשבונות השקעה, לפחות שתי פנסיות, קרנות השתלמות, קרן חירום וחסכונות ללימודים, לחתונות ולפרישה מוקדמת. לכן **מבוטל** הכיוון של שדה יתרה בתוך `Financial Goals`. מפרידים בין:

1. **חשבון / מוצר** — איפה הכסף מוחזק.
2. **מטרה** — בשביל מה חוסכים (`Financial Goals`, קיים).
3. **תנועות** — הפקדות ומשיכות.
4. **יתרות ושווי** — בנקודות זמן.
5. **נזילות ומיסוי** — מאפיינים של החשבון.

חשבון אחד יכול לשרת כמה מטרות, ומטרה אחת יכולה להיתמך מכמה חשבונות.

## 1. ממצאי האודיט (קריאה בלבד)

מקורות: `schema_cache.json` (סונכרן לאחרונה 06/10/2026 דרך Airtable MCP), `airtable_schema.py`, `core/financial_control/*`. **לא נעשתה שאילתה חיה ל-Airtable בסשן הזה**; לפני סכמה חייבים reconcile חי.

| טבלה / מודול | מה יש | מתאים לחשבון? |
| --- | --- | --- |
| `Financial Goals` | מטרה: יעד, קטגוריה, תקופה, `Contributes To` (היררכיה של מטרות) | **לא** — זו מטרה, לא מקום החזקה (החלטת בעלים) |
| `Financial Progress Events` | יומן append-only: `Goal` (קישור), `Amount`, `Kind`, `Occurred At`, `Source`, `Source Ref`, `Idempotency Key`, `Superseded By`, `Financial Owner` | **כן, כיומן תנועות** — כולל idempotency, ביטול (supersede), owner-scope וכתיבה דרך ה-FCC writer. חסר: קישור לחשבון, סוג תנועה למשיכה/יתרה, רמת אימות |
| `Assets` | נדל"ן: `Mortgage Balance`, `Ownership %`, `Equity`/`My Equity` (נוסחאות), `Sale Date/Amount`; `Asset Type` כולל `Other` | **לא** — אזור "נכסים והון" מסכם `total_value`/`equity` על כל הנכסים הפעילים; חשבון השקעות שם יזהם סיכומי נדל"ן ויצריך שדות שלא רלוונטיים |
| `Loans` | התחייבויות; יתרה מעודכנת ידנית (`Outstanding Principal for Early Closure`) | לא טבלה, אבל **תבנית**: עדכון ידני מדי כמה חודשים + אימות מול נתון חי |
| `Payments`, `Charges`, `Expenses` | תזרים עסקי | לא — `Payments` עסקי בלבד |
| `Recurring Obligations` | התחייבות חוזרת (הוראת קבע), לא יומן בפועל | לא |
| קוד FCC | `calc.deposit_status` / `deposit_history` (הפקדות מול רמה קבועה), `savings_release`, `assets.personal_equity` | אין שום ישות "חשבון" או "יתרת תיק" בקוד או בסכמה |

מסקנה: **אין טבלה קיימת שמתאימה לחשבונות פיננסיים.** `Financial Progress Events` מתאימה כיומן התנועות אחרי הרחבה קטנה; החשבון עצמו דורש ישות חדשה.

## 2. המודל המינימלי המוצע

### 2.1 טבלה חדשה אחת: `Financial Accounts`

| שדה | הערה |
| --- | --- |
| `Name` | שם החשבון / המוצר |
| `Account Type` | בחירה: `investment` · `pension` · `study_fund` · `emergency` · `education_savings` · `savings` · `other` (ללימודים / אירועים / פרישה מוקדמת — כמטרות, לא כסוגי חשבון, ראו 2.3) |
| `Institution` | בית השקעות / חברה מנהלת / בנק (טקסט חופשי) |
| `Financial Owner` | קישור ל-`Profile` (כמו בשאר טבלאות ה-FCC; owner-scope זהה) |
| `Status` | `active` · `closed` |
| `Liquidity` | בחירה: `immediate` · `locked_until_date` · `age_based` · `unknown` |
| `Liquid From` | תאריך (כשהנזילות קבועה בזמן) |
| `Tax Treatment` | בחירה תיאורית: `taxable` · `tax_advantaged` · `pension_rules` · `unknown`, ובנוסף `Tax Notes` (טקסט). **תיאור בלבד — לא חישוב.** |
| `Management Fee %` | דמי ניהול שנתיים כפי שדווחו (אופציונלי) |
| `Opened At`, `Notes` | |

אין שדה יתרה בטבלה: היתרה היא עובדה בנקודת זמן ולכן נגזרת מהיומן (2.2).

### 2.2 הרחבה של `Financial Progress Events` (בלי טבלה נוספת)

- שדה חדש `Account` — קישור ל-`Financial Accounts` (אופציונלי; אירועי מטרות קיימים לא משתנים).
- שדה חדש `Verification` — `self_reported` (ברירת מחדל) · `statement` · `bank_or_fund_confirmed`. מממש את ההחלטה "יתרה משוערת עם אפשרות לאמת".
- ערכי `Kind` חדשים: `withdrawal`, `balance_snapshot` (שווי מדווח בתאריך), `fee`.
- **תאימות לאחור:** `calc.parse_events` מדלג על `Kind` לא מוכר (`kind not in EVENT_KINDS`), ולכן אירועים חדשים אינם נספרים בחישובי המטרות הקיימים עד שנוסיף אותם במפורש.
- הכתיבה נשארת דרך זרימת האישור הקיימת של ה-FCC (טיוטה ← "אשר"); אין כתיבה אוטומטית.

**חלופה שנדחתה:** טבלת `Account Movements` נפרדת. נקייה יותר סמנטית, אבל משכפלת idempotency, supersede, owner-scope ותשתית כתיבה שכבר קיימים — הפרת עיקרון "בלי כפילות".

### 2.3 יחס רבים-לרבים בין חשבון למטרה

אירוע אחד נושא גם `Goal` וגם `Account`, ולכן הפקדה מחשבון A למטרה X ומחשבון B למטרה X, או מחשבון A למטרות X ו-Y, נרשמות בלי טבלת קשר. התקדמות מטרה = סכום האירועים שלה. **שווי** של חשבון משותף בין כמה מטרות מחייב הקצאה (אחוזים); זה נדחה לשלב מאוחר עם טבלת `Goal Allocations` — **לא נבנה עכשיו** ונדרש אישור נפרד כשיהיה צורך.

### 2.4 מיפוי סוגי החיסכון

| סוג | ייצוג |
| --- | --- |
| פרישה מוקדמת (השקעות) | חשבון `investment` + מטרה |
| קרן חירום | חשבון `emergency` (`Liquidity=immediate`); המטרה `emergency_fund` כבר קיימת ב-FCC |
| שתי פנסיות ויותר | חשבון `pension` לכל קרן; היעד הקיים `long_term` ("תכנון פנסיוני") נשאר מטרה |
| קרנות השתלמות | חשבון `study_fund` עם `Liquid From` ו-`Tax Treatment` |
| לימודים / חתונות / אירועים | מטרות עם יעד כספי ותאריך; החשבון שמחזיק את הכסף נבחר בנפרד |

## 3. משיכות ויעילות מס — מה לא קובעים

אין כלל אוטומטי "למשוך תמיד מהחשבון האחרון". יש להבחין בין שלושה דברים נפרדים: **נזילות** (מה זמין ומתי), **הטבות מס** של המוצר, ו**בסיס העלות** של ההשקעות בתוכו. החשבון שנפתח אחרון אינו בהכרח זה שרווחו החייב הנמוך ביותר: זה תלוי בניירות, בתאריכי הקנייה, בכללי המס ובסוג המוצר.

- בגרסה הראשונה נשמר רק מידע תיאורי (`Liquidity`, `Liquid From`, `Tax Treatment`, `Tax Notes`).
- תכנון סדר משיכות דורש בסיס עלות לפי רכישות (lots) ונוסחאות מס מאומתות; **מחוץ להיקף** ודורש SPEC נפרד וייעוץ מקצועי. אין לקוד מס ישראלי בלי אישור בעלים.
- המנוע הקיים (`tax_model` אופציונלי) נשאר ללא שינוי.

## 4. השפעה על שני המסלולים

**מסלול A — סימולטורים (Portfolio Lab).** כיום סימולציה של תיק אחד. הרחבה בשלבים, בלי להעמיס על המנוע בבת אחת:

- **A1** — תחזית לכל חשבון בנפרד (הרצת המנוע הקיים פר חשבון) וסכום מאוחד בשכבת ה-view בשרת. המנוע לא משתנה.
- **A2** — מטרות ומועדי נזילות: מתי הכסף זמין מול מועד היעד.
- **A3** — משיכות מתוזמנות (סכום ותאריך שנבחרו ידנית).
- **A4** — תכנון סדר משיכות לפי מס: רק אחרי SPEC נפרד (סעיף 3).

**מסלול ב — המסך (תכנון חיסכון לטווח ארוך).** שתי הלשוניות הקיימות נשארות בשלב הראשון.

- **B0** — קיים: #1313, #1314 (ממוזגים) ו-#1315 (הפקדות; לא תלוי בסכמה).
- **B1** — רשימת חשבונות וסיכום הון מאוחד (קריאה בלבד).
- **B2** — התקדמות לכל מטרה.
- **B3** — עדכון יתרה ידני (`balance_snapshot`) ואימות — דרך זרימת האישור של ה-FCC.

**תלות משותפת D1 — מודל החשבונות (סעיף 2).** אינה תוכנית שלישית: A1 ו-B1 תלויים בה, ולכן היא מקדימה את שניהם.

## 5. סדר ביצוע מוצע (כל שלב דורש אישור נפרד)

1. אישור SPEC זה (כולל שאלות פתוחות).
2. Reconcile חי של Airtable (קריאה בלבד) לפני כל שינוי.
3. יצירת הסכמה (`Financial Accounts` + שדות/ערכים ב-`Financial Progress Events`) באישור מפורש, עם עדכון `schema_cache.json` ו-`airtable_schema.py`.
4. D1 ב-backend: קריאה בלבד + בדיקות. אחריו B1 ו-A1 במקביל.

## 6. שאלות פתוחות לבעלים

1. האם חשבונות של בן/בת זוג או ילדים נכללים בהון המשפחתי? כיום `Financial Owner` הוא בעלים יחיד.
2. האם מספיקה רשימת `Account Type` שלעיל, או חסר סוג (למשל ביטוח מנהלים, קופת גמל להשקעה)?

4. האם להשאיר את `Goal Allocations` (הקצאת שווי חשבון בין מטרות) לשלב מאוחר, כפי שמוצע?
