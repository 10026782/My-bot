## 4. מה ניתן במקביל ומה לא

**במקביל ללא התנגשות קבצים (אחרי A0 ו"אישור המימוש"):**
- **A ‖ C ‖ B1** — שלוש קבוצות קבצים חדשים שונים בלי חפיפה. ההסכמה היחידה ביניהן היא `unifiedScreenTypes.ts` (A0). B1 יכול לרוץ מול mocks של המודל.
- כל אחד מהם מוסיף רישום טסט אחד ל-`package.json` → **נקודת התנגשות קטנה**: מוזגים לפי סדר ופותרים ידנית (שורה בשרשרת); לחלופין שלב אחד מרכז את שלושת הרישומים.

**חייב להיות טורי:**
1. A0 לפני A/B1/C.
2. B2 אחרי B1 **ואחרי שלב 2 של מקורות המימון** (`GOAL_FUNDING_SOURCES_SPEC` §5א) — שניהם נוגעים ב-`FamilyWealth.tsx`.
3. D אחרי הכול.
4. כל שלב עם CHANGELOG: שורת `## Unreleased` — קונפליקט צפוי ופתרון "שני הצדדים נשמרים"; למזג לפי סדר.

**הפרדה מעבודות אחרות שפתוחות כעת:**
- שלב 2 של מקורות המימון (UI בלשונית "מימון יעד" + שינוי API שרת לחשיפת "צפוי לתאריך היעד" לכל חשבון) — **לא נוגעים בקבציו**; המסך המאוחד מציג רק את שדות התשובה הקיימים, ויותאם לשדה החדש בשלב מאוחר אחרי שהוא ממוזג (§6).
- #1350 (ניסוח כרטיס השווי הנקי): ה-model של המסך מייבא את `netWorthModel`, ולכן מתאים אוטומטית; ראו §6.

## 5. כללי "אל תכפיל חישוב" (מחייבים לכל שלב)

- שום חשבון/סכום/ממוצע/הפרש בלקוח. מספר מוצג רק כפי שהשרת החזיר.
- שימוש חוזר ב-`netWorthModel` (ניסוח C2), `savingsTabModel`/`familyWealth.ts` (היסטוריית הפקדות) ובפונקציות הקיימות; אסור להעתיק לוגיקה.
- אין כתיבה: אין קריאת `POST` שכותבת מהמסך; `funding/plan` ו-`pace` קוראים בלבד. שמירת תוכנית ופעולת מעקב נשארות במסכים הקיימים.
- אין סכום כולל, אין "הון + צפוי".
- מבחן ביקורת נדרש לכל שלב: grep לפעולות `+`/`reduce` על שדות כסף בקבצים החדשים.
