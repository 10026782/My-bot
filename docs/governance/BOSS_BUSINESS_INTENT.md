## 1. מה אנחנו בונים

BOSS היא פלטפורמת AI לניהול ותפעול עסקים המחברת בין Telegram, WhatsApp, מערכות עסקיות, CRM וכלי אוטומציה.

היא נבנית תחילה עבור בעל המערכת ועסקיו.
אם תהיה יציבה, אמינה ושימושית מספיק, תוכל בהמשך לשמש גם עסקים אחרים.

## 2. משפט הכיוון המחייב

אנחנו לא בונים סוכן חכם שמנסה לנהל מערכת.

אנחנו בונים מערכת חכמה, יציבה וחסכונית, שמשתמשת בסוכן רק במקום שבו הוא מוסיף ערך.

## 3. עקרונות שכבר הוכרעו

- אמינות לפני נוחות.
- מידע חסר עדיף ממידע משובש.
- פעולה שאין דרך אמינה להבין, לאמת ולבצע — אינה מתבצעת.
- זרימה תקינה ויעילות לפני פיצ'רים וחידושים.
- deterministic first.
- פעולות עסקיות הן חוזים ויכולות מוגדרות.
- הסוכן הוא ממשק שפה ורכיב reasoning, לא מנהל המערכת.
- מקור אמת אחד לכל אחריות.
- owner אחד בכל שלב.
- תגובה סופית אחת לכל turn.
- evidence לפני טענה.
- כביש אחד שממנו מתפתחות הסתעפויות, ולא כמה מסלולים מקבילים.

## 4. כלל הזהב לפני כל פיצ'ר

לפני יישום כל פיצ'ר יש לשאול:

**האם השימוש ב-BOSS פשוט, מהיר, ברור או בטוח יותר מפתיחת הכלי המקורי וביצוע הפעולה ישירות?**

אם קל יותר לפתוח את הכלי המקורי ולמלא את הפרטים, BOSS לא מילאה את תפקידה באותה פעולה.

הפיצ'ר צריך להפחית לפחות אחד מהבאים:

- מספר פעולות המשתמש;
- כמות המידע שהמשתמש מזין;
- הצורך להכיר את מבנה הכלי;
- מעבר בין מערכות;
- זמן;
- סיכון לטעות;
- מעקב ידני.

אם אין יתרון ברור:

- SIMPLIFY
- AUTOMATE_MORE
- KEEP_NATIVE
- REMOVE

## 5. הכביש המרכזי

```
User request
→ intent / request type
→ structured extraction when needed
→ business capability
→ validation and permissions
→ ActionContract or defined process
→ approval when required
→ authorized execution
→ evidence
→ semantic state
→ one user response
→ audit and learning
```

## 6. תפקיד הסוכן

**מותר:**

- הבנת שפה;
- חילוץ מידע;
- זיהוי עמימות;
- סיכום;
- ניסוח;
- הצגת חלופות;
- סיווג לפי החלטות קיימות;
- reasoning במקום שבו אין כלל אמין ופשוט.

**אסור:**

- לנחש tokens פנימיים;
- להמציא תהליך עסקי;
- לבחור ללא הגבלה מכל הכלים;
- לקרוא מידע לא נדרש;
- להרחיב משימה פשוטה לחקירה;
- לעקוף validation, permissions או approval;
- לקבוע success ללא evidence;
- להמשיך לאחר שהבעלות עברה לרכיב אחר;
- ליצור מקור אמת מקביל.

## 7. תפקיד ה-Librarian

בעל העסק קובע את הכיוון.

ה-Librarian:

- מחלק למסלולים ותתי-נושאים;
- מזהה חפיפות;
- מזהה סתירות;
- מזהה תלויות;
- מפריד בין תכנון, קוד קיים, wiring ו-runtime פעיל;
- מסווג מול המסמך העסקי.

הסיווגים:

- **KEEP**
- **ADAPT**
- **MERGE**
- **FREEZE**
- **REMOVE**
- **VERIFY**
- **OWNER_DECISION**

ה-Librarian אינו משנה את ההחלטה העסקית ואינו מקבל החלטת בעלים.

## 8. משפט הסמכות

בעל העסק קובע מה המערכת צריכה להשיג.

ה-Librarian מסווג את הידע והתכניות לפי ההחלטה.

הארכיטקטורה מתרגמת את ההחלטה לאחריות ולחוזים.

הקוד מממש את החוזים.

ה-runtime והראיות מוכיחים שהמערכת אכן פועלת בהתאם.

## Change policy

שינוי בכוונה העסקית (סעיפים 1–8 למעלה) דורש החלטת **owner** מפורשת — לא Librarian, לא סוכן, לא consensus טכני. שינוי כזה מעדכן את `Version`/`Last updated` בראש המסמך (ראו כלל ה-Definition of Done ל-`ROADMAP.md` ב-`AGENTS.md` — אותו עיקרון חל כאן: עדכון תוכן בלי עדכון התאריך/הגרסה אינו שינוי שלם).

הרחבת scope עצמאית — הוספת עקרון, סעיף, או ניסוח שלא הוכרע ע"י ה-owner במפורש — אינה מותרת בשום עדכון, כולל עדכון שמבצע Claude Code/Librarian מטעם משימה אחרת.

## המסמך אינו מקור אמת למצב implementation

מסמך זה קובע **כוונה**, לא סטטוס. הוא אינו מדווח אילו שכבות בנויות, מחוברות, פעילות, מאומתות, או flag-on/flag-off. למצב ה-implementation בפועל — ראו `ROADMAP.md`, `AI_CONTEXT.md`, `CHANGE_CONTROL_LOG.md`, ו-`BUG_AUDIT_LOG.md`, בהתאם לכללי "מקור אמת יחיד" הקיימים כבר ב-`docs/governance/BOSS_UNIFIED_MASTER_PLAN.md` §3.

אין להכניס לתוך מסמך זה תכנון PR מפורט, timeline, או פירוט טכני של שכבה ספציפית — אלה שייכים ל-`ROADMAP.md`, ל-SPEC-ים תחת `docs/architecture/`, ולשערי `PLANNING_GATE.md`.
