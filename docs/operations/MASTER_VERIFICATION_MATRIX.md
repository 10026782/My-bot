## 0. Cross-cutting findings (apply to the whole matrix)

1. **The `@pytest.mark.airtable`/`integration`/`live` exclusion mechanism is currently vacuous.** `conftest.py` defines these markers and CI's default run excludes them (`-m "not integration and not airtable and not live"`), but a repo-wide grep found **zero test files that actually use any of the three markers**. In practice nothing is excluded by marker today — everything CI executes is mocked by convention, not by marker enforcement. If a future test needs real Airtable/Telegram/Twilio access, nothing currently stops someone from adding it unmarked, where it would either hang or fail against CI's fake credentials and blocked network (see below) — a fail-loud outcome, not a silent gap, but worth knowing the marker system itself is not doing any work right now.
2. **A second, narrower false-pass class exists beyond the one `CI_TEST_HARNESS_FALSE_PASS_20260830.md` fixed.** That audit fixed files with *zero* runner (0 tests silently executed). It did not catch files that **do** run under `pytest -x` but use non-raising `chk()`/assert-and-continue helper patterns *inside* real `def test_...()` functions — such a function always returns normally regardless of what its internal checks found, so pytest reports it as passing no matter the outcome. Two confirmed instances: `test_phase_4b0_1b_concurrency.py` (ActionGateway striped-lock race check) and `test_phase_4b0_1c_concurrent_approvals.py` (three-store approval concurrency check). Both are structurally incapable of failing CI's generic loop today. `test_phase_4b0_1b_concurrency.py` happens to be genuinely exercised elsewhere (TC10's dedicated `scripts/run_isolated_regression.py --repeat 2` step, which uses real assertions against a real Postgres `DATABASE_URL`); `test_phase_4b0_1c_concurrent_approvals.py` has no such backstop anywhere. **Logged, not fixed**, per this audit's scope — see the Approval and ActionGateway rows below.
3. **One contradiction in `CURRENT_SYSTEM_EXECUTION_MAP.md` was stale at the time of this audit and is now reconciled.** Its older §8/§10 finding #6 described the broken Contacts adapter; PR1153 is now on `origin/main`, calls `tools.contact_resolver.resolve()`, and adds/retains regression coverage in `test_core_reasoning.py`. A regression would be caught even while the gating flags (`FEATURE_DECISION_HUB`/`FEATURE_CORE_REASONING_LEADS_STATE`) stay off. See the Contact and Decision Hub rows.
4. **CI's Airtable credentials are fake and network egress to `api.airtable.com` is actively blocked** (`ci.yml`'s "Block network egress to Airtable" step). Combined with finding #1, this means: nothing CI runs today can be hitting real Airtable — every test that appears to exercise an Airtable write is necessarily mocked at the `airtable_gateway`/`airtable_create`/`airtable_patch`/httpx boundary. This is consistent across every capability below; it is called out once here rather than repeated 23 times.
5. **A real PostgreSQL service exists in CI** (`DATABASE_URL` pointing at a CI-only `boss_bot_ci` database), so anything touching `FEATURE_ATOMIC_CLAIMS`/durable turn-state/ActionContract persistence can be — and in a few cases genuinely is (TC10) — tested against a real database, not just a mock. This is the one infrastructure dependency CI does not have to fake.
