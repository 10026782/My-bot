**Single construction site confirmed**: `grep -n '^\s*ActionContract('` over the whole file returns exactly one hit, inside `propose_action()` at `core/action_gateway.py:1961`. No other call site instantiates `ActionContract`.

**`propose_action()`** (`core/action_gateway.py:1697-2000+`): calls `resolve_canonical_tool()`/`resolve_canonical_call()` first (BUG-CANONICAL-TOOL-WIRING); for `trusted_source=="agent"` blocks a new proposal if `find_live_contracts()` shows any pending contract (BUG-122, one-live-mutation policy); computes `business_action_fingerprint = hash(tenant+user+tool+normalized_payload)` via `compute_business_fingerprint()` (:1802); dedup logic branches on the existing contract's status — `pending`→block, `completed`/`executed`→`_handle_duplicate_executed()`, `rejected`→block unless `trusted_source=="deterministic_create_task"` (BUG-153 explicit-reconfirmation carve-out), `approved`/`executing`/`outcome_unknown`→block (:1858-1911). Fingerprint claiming uses `ExecutionLedger.claim_fingerprint_cas()`, an atomic compare-and-set over an in-process token map (BUG-157, up to 5 retries / 2s total wait budget, :1834-1930) to close a race between two threads (e.g. scheduler background thread vs main request thread) both seeing "no blocking contract" before either saves. `requires_approval` is fail-closed cross-checked against `tool_registry.needs_approval()` — registry wins if caller passed `False` (BUG-077, :1979-1988). Status set to `"pending"` if `requires_approval` else `"approved"` (:1980-1982), then `self._ledger.save(contract, claim_token=...)`.

**`approve()` → `_execute_contract()`** (`:3408-3520+`): `approve()` is a thin wrapper serializing `_approve_unlocked()` per `contract_id` via a striped lock (`self._approve_locks[hash(contract_id) % N]`, :3408-3416) so two concurrent `approve()` calls for the *same* `contract_id` can never both observe `"pending"`. `_approve_unlocked()`: fetches contract, rejects if not found or `status != "pending"` (:3438-3447); authorization check is policy-dependent — `APPROVAL_POLICY_SELF_CONFIRM` requires `approver == contract.canonical_user_id` + internal role; default `APPROVAL_POLICY_APPROVAL` requires `_has_approval_authority(approver_role)`, re-checked fresh against the live `approver_role`, never trusting `contract.actor_role` (BUG-074/076, :3453-3468). Fails closed if `_tool_executor` is `None` (:3470-3479). Durably transitions to `"approved"` via `self._ledger.update_status(...)` *before* execution (:3483-3491), then calls `self._execute_contract(updated)` (:3512).

`_execute_contract()` (:3519+): when `FEATURE_ATOMIC_CLAIMS` is enabled (or `tool_name=="recruitment_write"` unconditionally, :3722), reconstructs a frozen `Identity` from the contract's actor snapshot (fails closed if any of `actor_role`/`actor_external_id`/`tenant_id`/`actor_user_id` missing, :3733-3757), then gates dispatch through `core.action_gateway_atomic_executor.execute_with_atomic_claim()` (:3763-3777) instead of calling the executor directly.

**PostgreSQL atomic claim** (`core/action_gateway_atomic_executor.py` + `core/atomic_claim_repository.py`): `execute_with_atomic_claim()` — flag OFF → calls `executor_fn` directly (backward compatible), except `require_claim=True` (`recruitment_write`) forces a hard failure if PG unavailable (`aae.py:53-60`). Flag ON → `claim_contract_execution()` does `INSERT ... ON CONFLICT DO NOTHING RETURNING contract_id`: row returned = this caller wins and owns execution; `None` = another caller already owns it, stop (`atomic_claim_repository.py:9-12`). Result types: `acquired`/`already_claimed`/`idempotency_conflict`/`contract_identity_conflict`/`unavailable`(PG down, fail-closed)/`disabled`/`error` (:44-58). Claim status lifecycle once acquired: `executing`→`completed`|`failed`|`outcome_unknown` (never auto-retried, :18-21). **File header states `FEATURE_ATOMIC_CLAIMS` is "Staging only... flag is OFF in production"** (`action_gateway_atomic_executor.py:1-8`) — this is the concurrency-safety layer BusinessDraft's confirm path would want to build on, and it is not yet live.

**ExecutionLedger** (`:680-1539`): RAM dict (`_store`, `_by_fingerprint`, `_by_user`) is always the cache, never sole source of truth once a repository is configured. `save()` (:~870): if `self._repository` set, persists there first and only publishes to RAM on success (raises `ActionContractPersistenceError` otherwise — "a failed durable write can never leave an actionable RAM-only contract", comment above `save()`). Repository wiring is gated by `FEATURE_ACTION_CONTRACT_PERSISTENCE` at module load (`:4788-4801`, `_build_action_contract_repository()`): flag OFF → `repository=None`, pure RAM, and "the legacy `_build_airtable_writer()` is intentionally never activated." **Across a restart with the flag OFF**: all RAM state is lost — every draft/pending/approved contract vanishes; `find_by_id`/`find_by_fingerprint` return `None` for anything not freshly re-proposed. With the flag ON, `find_by_id`/`find_by_fingerprint`/`find_live_by_user` fall back to `self._repository.get()`/lookups on cache miss (:~900-935) — restart-safe recovery.

**Status enum** (from field comment :307 + confirmed usages): `"draft"` → `"pending"` → `"approved"` → `"executing"` → terminal `"completed"` | `"failed"` | `"outcome_unknown"` | `"rejected"` | `"superseded"` (superseded = a second, unrelated message interrupts a pending contract, :1087/3067). Legacy alias `"executed"` == `"completed"` (:2697, :3537 comment "legacy RAM-only alias, not a 5th outcome").

**DIAMOND PATH nested-entity continuation**: `ContinuationRef` (frozen dataclass, `commercial_completion.py:797-843`) is a typed pointer — `session_key`, `channel`, `nested_entity`, `return_field`, `nonce` — from a queued nested-entity ActionContract back to the parked parent `CompletionSession` (never a serialized copy of the session; `session_store.py`'s `PersistentSessionStore` stays sole owner). `nonce` is the actual correlation key (matching `nested_entity`+`return_field` alone only proves shape, not identity). `CompletionSession.begin_nested()`/`resume_parent()`/`abandon_nested()` (`commercial_completion.py:912-964`) push/pop a stack of `_CompletionFrame`s. The resume path: `core/action_gateway.py`'s `_apply_diamond_post_approval_hook()` (:2404-2452) is a shared tail called by all three text-confirmation resolvers, dependency-injecting `post_approval_hook` (never importing `app.py` — that would trigger full Flask/bot startup, :2417-2429) — `app.py::_apply_diamond_post_approval_continuation()` (`app.py:3793-3871`) is the actual hook, reachable only when `contract_after.status in ("completed","executed")` (fail-closed: rejected/failed/pending never continues). It delegates to `_resolve_diamond_path_continuation()` (`app.py:3476-3560+`), which loads the parked session via `session_store.lead_sessions.get_commercial_completion(continuation_ref.session_key, channel=...)`, validates via `CommercialCompletionRouter.resume_nested()` against the expected `nested_entity`/`return_field`/`nonce`, and either folds the newly-created record id into the parent (resume) or `abandon_nested()`s the parked frame on mismatch/rejection (never leaves an orphan). This is exactly a prototype multi-step draft→create-linked-entity flow scoped to Contact/Organization-under-Deal; a future BusinessDraft linked-record UX should treat `ContinuationRef`/`CompletionSession` as the thing to either reuse or explicitly supersede, not duplicate.

## 2. `tools/dispatcher.py` (1461 lines)

`_validate_execution_proof()` (:437-466): for `tma_write`/`external_execution.submit`, only requires `execution_context.get("contract_id")` truthy. For every other approval-sensitive tool, requires all of: `contract_id`, `approved_by`, `tool_name`, `tenant_id`, `canonical_user_id`, `business_action_fingerprint`, `status` (:445-448) — then additionally checks `status in {"approved","executing"}`, `tool_name` match, `tenant_id` match against `identity.tenant_id`, `canonical_user_id` match against `identity.memory_key`, and recomputes `ActionGateway.compute_business_fingerprint()` over the actual inputs to confirm the proof matches the real payload (:452-465) — i.e. the proof is cryptographically bound to the specific action, not just "some approval exists."

CREATE/UPDATE routing: `dispatch_tool()` uses a `match name:` statement (:556) with `case "airtable_add":` at :632 and `case "airtable_update":` at :850, alongside 20+ other tool cases (`crm_*`, `gmail_*`, `calendar_*`, `tma_write`, etc.).

`_TENANT_AWARE` set (:704-709): `{"Leads", "אנשי קשר (Contacts)", "Contacts", "עסקאות (Deals)", "Deals", "תשלומים (Payments)", "Payments"}` — used only inside the `airtable_add` case to `fields.setdefault("tenant_id", tenant_id)`. **Tasks (`"Tasks"`/`"משימות (Tasks)"`) is not in this set** — confirmed: a Task record written via `airtable_add` never gets a `tenant_id` field injected. Separately, `enforce_tenant_scope()` (`tools/airtable_security.py:96-165`) is still called unconditionally for every `airtable_add`/`airtable_update` (`dispatcher.py:709-716`) and is a hard no-op for internal roles (owner/staff, :131-133) — the only place Tasks appears in `airtable_security.py` is a `partner`-role read-only domain filter map (`{"Tasks": "Domain", "משימות (Tasks)": "Domain", ...}`, :117) used solely for `airtable_get`, not writes. **Net: Tasks does not participate in tenant-scoped field injection on writes** — the prior audit finding holds. `_ALIAS_MAP` (:62-63+) maps `"Tasks"→"משימות (Tasks)"` etc. `_DEDUP_FIELDS` (:47-49) maps table→dedup field, e.g. Tasks dedup on `"כותרת המשימה"`.

## 3. `event_bus.py` (440 lines)

`PendingActionsStore` (:28-178): plain RAM dict `{action_id: {action, payload, chat_id, label, created, expires}}`, `PENDING_TTL_MINUTES=30` (:26). `add()` mints a short uuid4[:8] id (:41-56). Expiry is lazy — checked on every `get()`/`pop()` (deletes on read if past `expires`, :58-79) — plus an explicit `cleanup()` (:168-178) that sweeps all expired entries; nothing calls `cleanup()` on a timer in this file (a scheduler job elsewhere would need to). `pop()` is lock-guarded (LL-13, :70-76) so two near-simultaneous confirms can't both grab the same entry. `EventBus` (:236-339) wraps one `PendingActionsStore` instance and exposes `request_approval()`/`confirm()`/`reject()`/`pop()`/`peek()`, routing to `bus.emit(f"{action}.confirmed", ...)` handlers.

Only one production construction site: `event_bus.py:438` — `pending = PendingActionsStore()` (module-level singleton, paired with `bus = EventBus(pending)`). All other `PendingActionsStore(` hits are test files (`test_approval_gateway_safety.py`, `test_approval_requeue.py`, `test_ll13_double_execution.py`) constructing isolated instances. Direct importers of the singleton `pending`/`bus`: `app.py` (multiple sites, e.g. :1977, :4115), `core/approval_queue_recovery.py:122`, `scheduler.py:71`, `abandoned_lead_worker.py`, `core/lead_recovery.py`, `email_inbound.py`, `followup_engine.py`, `media_handler.py`, `tma_api.py:435` — this is the legacy `.confirmed`-event pending-approval mechanism, structurally separate from `ActionContract`/`ActionGateway`, and is the retirement-matrix surface.

## 4. `tools/approval_actions.py` (470 lines)

Per its own header (:1-16): `media_save_to_memory`, `send_followup`, `send_recovery` were historically driven by ad-hoc `event_bus.subscribe("<action>.confirmed", ...)` handlers fed by `event_bus.request_approval()` (the mechanism in §3). `ActionGateway` only knows how to execute a contract via `dispatch_tool(tool_name, tool_inputs, contract_id)`, with no generic "run an arbitrary callback" path — so this module reimplements those three actions as real dispatcher tool cases (registered in `tool_registry.py`, routed in `dispatcher.py`'s `match`) returning the C53-A structured `{ok, tool, external_id, evidence, user_message}` contract (`_tool_result()`, :26-41), so they can be proposed/approved/executed through `ActionGateway` like any other tool instead of the legacy event_bus flow. Also holds `tma_write` (:276+) and its claim-verification helper `_verify_active_execution_claim()` (:239-274), which independently confirms a live PostgreSQL claim row rather than trusting a caller-supplied dict.
