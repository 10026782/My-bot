## 1. `core/lead_service.py`

**Purpose**: sole canonical writer for Lead records (module docstring, L1-17): "No other code path should call `tools.airtable_gateway.airtable_create`/`airtable_patch` on `table='Leads'` directly." Deliberately bypasses `tools/dispatcher.py` (L11-14: Leads writes are blocked there for `source="agent"`; this is a trusted, non-agent path like `lead_capture.py`).

**Signatures**:
- `create_lead(identity, payload: LeadPayload, *, source_module: str, existing_id: Optional[str]=None, write_event: bool=True, manage_action_contract: bool=True) -> LeadCreateResult` (L356-364)
- `update_lead_fields(identity, record_id: str, fields: dict, *, source_module: str) -> LeadCreateResult` (L545-551) — narrower: caller must supply a resolved `record_id` + explicit fields; gateway failure is terminal, no direct-write fallback.
- `find_existing_lead(name: str, phone: str) -> Optional[str]` (L239) — dedup.

**Owner resolution**: `resolve_owner(identity, owner_user_id="") -> tuple[Optional[str], str]` (L120-137) — defaults to creator (`identity.user_id`) via `tma_api._resolve_profile_record_id()`, same resolver Tasks.Owner uses. Hard-enforced (L402-421): an unresolvable Owner **blocks creation outright** — no lead is ever saved without one (this replaced an earlier warn-and-proceed fallback).

**Dedup (`find_existing_lead`, L239-284)**: queries Airtable "Leads" via `list_records` with formulas from `_search_formulas` (L287-293: `contains(Name)+equals(phone)`, then bare `equals(phone)`, then bare `contains(Name)`); only an **exact phone match** counts as same-lead when phone is given (name-only match rejected, per BUG-094 in the old handler). `create_lead()` does its own lookup only if `existing_id is None` (L425-426) — callers like `lead_candidate_handler.py` pass a pre-resolved id to skip a second lookup.

**ActionGateway integration** (L438-480): when `manage_action_contract=True` (default), calls `action_gateway.action_gateway.propose_action(tenant_id, canonical_user_id=identity.memory_key, tool_name="airtable_update"|"airtable_add", tool_inputs=..., origin_channel, origin_chat_id=identity.memory_key, requires_approval=False, identity=identity)` before writing — this is the dedup fingerprint/idempotency ledger (BUG-077, preserved not stripped). `manage_action_contract=False` is used by the N18 Phase 3 "ActionGateway dispatch executor" path, which already owns an approved outer contract (avoids nested ActionContracts for the same write). After the physical write, contract status is updated via `contract_ledger.update_status(contract_id, "completed"/"executed" if ok else "failed")` (L510-526); failure to persist that status yields `action="lifecycle_persistence_failed"` — a distinct terminal state, never silently dropped.

**"lead_draft" state object** (L790-830, `new_empty_draft`/`build_draft_from_text`): a plain dict — `{name, phone, domain, source, note, channel, mode, awaiting_field, callback_token?, set_at?}`. `mode` ∈ `"filling" | "edit_choice" | "review"` (edit_choice comes from `core/draft_flow.py`'s generic state machine, not literally in this file). `DRAFT_FIELD_ORDER=("name","phone","domain","source","note")`, `DRAFT_REQUIRED_FIELDS=("name","phone","domain")` (L753-754). Generic per-field metadata/validation is `LEAD_FIELD_METADATA` (L1017-1026, using `core/draft_fields.py`'s `FieldMetadata`), and the whole thing is wired into a generic `DraftSpec` (`LEAD_DRAFT_SPEC`, L1030-1039, from `core/draft_flow.py`) — i.e. Lead's own plug-in into a **generic, entity-agnostic draft state machine** already built and reused elsewhere. (Confirmed separately: `core/draft_fields.py` is merged to `origin/main` and this import is live, not stale/unmerged.)

**Idempotency**: relies entirely on the ActionGateway proposal (business-fingerprint dedup) plus `find_existing_lead` — no separate idempotency key/token scheme inside this file itself.

## 2. `core/lead_candidate_handler.py`

**Purpose** (L1-15): short-circuits the agent loop for explicit owner/staff lead-save patterns; feeds off `classify_ingress()`'s Tier 1-5 classification. Tier 4/5 → falls through to agent (never auto-writes). Tier 1/2 + `FEATURE_AUTO_CAPTURE=ON` → direct Gateway write. Tier 1/2 + flag OFF → preview+confirm. Tier 3 → clear ones write, ambiguous → needs_review.

**Three distinct pending-state mechanisms, all stored as top-level keys on the same session dict** (`session_store.py`'s per-sender session, see file 3):

1. **`lead_draft`** (Phase 1 "Lead Draft Card", the primary creation UX) — single-lead, field-by-field or free-text-prefilled fill/review/edit flow. Started by `_start_lead_draft()` (L913-925), state object defined in `lead_service.py` (above). Lifecycle states in code: `"filling"`, `"edit_choice"`, `"review"` (`draft["mode"]`), plus terminal outcomes via `TurnResult` status constants `STATUS_CANCELLED`, `STATUS_INCOMPLETE`, `STATUS_FAILED`, `STATUS_CONFIRMED` (from `core/turn_result.py`). Confirm/cancel: `_finalize_draft_confirm()` (L937-967, calls `draft_to_payload()` + `create_lead()`) / `_finalize_draft_cancel()` (L928-934) — shared by both the in-flow resolver `_resolve_lead_draft()` (L1024+) and `app.py`'s early-dispatch `resolve_lead_draft_confirmation()` (L1001-1021). Edit: handled generically by `core/draft_flow.py`'s `resolve_draft_reply()` against `LEAD_DRAFT_SPEC`.
   - Precedence guard `should_prefer_lead_draft()` (L970-998): true only for a `mode=="review"` card, and only if it's *more recent* (`set_at`) than both the Tier-1 ActionGateway bookmark (`last_prompted_contract`) and the Tier-2 batch preview (`pending_lead_preview`) — i.e. "whichever was shown to the user most recently wins," not a fixed hierarchy.
   - **The exact "regardless of FEATURE_ACTION_GATEWAY" comment** (L400-403, in `_propose_lead_write()`'s docstring): *""כן" resolves it through ActionGateway.approve() -> dispatch_tool() (app.py's confirm-word handling checks Gateway live contracts first, regardless of FEATURE_ACTION_GATEWAY) — so the confirmed write goes through the same dispatcher path as any other approved tool call, not a direct one-off airtable_add."* This is about **Tier-1** single-lead preview (`_propose_lead_write`), not the Lead Draft Card.

2. **`pending_lead_preview`** (Tier-2 batch preview, C89/BUG-058) — module: `session_store.py`, accessed via `lead_sessions.set_pending_lead_preview()`/`get_pending_lead_preview()`/`clear_pending_lead_preview()` (see file 3). Storage: **in the same Session dict that's RAM-cached + Airtable-Sessions-backed** — not a separate store. State shape (`_store_pending_preview`, L1540-1556 delegates to `session_store.set_pending_lead_preview`): `{"candidates": [...], "raw_text": str, "channel": str, "domain": str, "set_at": float}`. TTL 1800s (30 min), enforced on read in `session_store.get_pending_lead_preview()` (self-clearing, also syncs the clear to DB unlike `active_lead_candidate`'s lazier clear). Confirm/cancel: `resolve_pending_lead_preview()` (L1603-1653) — confirm calls `_handle_batch()` for **all** candidates at once (no partial/per-item selection: *"אין תמיכה ב-selection חלקי ('כן 1') — רק אישור/ביטול מלא לכל ה-batch"*, L1617); cancel just clears it. Precedence vs. Tier-1: `should_prefer_batch_preview()` (L1559-1600) — same recency-comparison pattern as `should_prefer_lead_draft`.

3. **`last_lead_candidate_batch`** (Section 4C, follow-up routing only, not a pending-action) — written post-write by `_save_batch_state()` (L1748-1772): `{"original_message_text": str, "detected_count": int, "processed_count": int, "per_lead": [{"name","phone","record_id","action","ok"}, ...]}`. Purely a completed-batch audit/follow-up cache (for "ומה עם השאר?"-style follow-up questions, `_handle_batch_followup()` L1775-1815) — it's written **after** the batch is already committed, not a confirm/cancel-pending mechanism.

**Batch confirm-all / per-item**: only confirm-all exists today (`resolve_pending_lead_preview`'s is_confirm branch calls `_handle_batch` on the whole candidate list). No per-item accept/reject UI for a batch is implemented — `_handle_mixed_batch()` (Tier 3, L1460-1535) comes closest, since it writes "high" confidence candidates and gateway-proposes each individually (looping `_propose_lead_write` per candidate, L1504-1517), so each Tier-3 "high" item does get its own individual Tier-1 ActionContract — but that's a byproduct of Tier-3's mixed-confidence design, not an explicit per-item UI on top of a stored batch.

## 3. `session_store.py`

**Purpose**: `PersistentSessionStore` (class def L223), singleton instance `lead_sessions` (constructed at module bottom, referenced everywhere). RAM LRU (`OrderedDict`, max 1000, L37/232-234) backed by Airtable `Tables.SESSIONS` (`Sessions` table) for restart-durability.

**Per-session schema** (`_new_session()`, L145-186) — one dict holds *everything*: `context_type` (default "lead", generic table reused for multiple contexts), `domain`, `channel`, `step`, `answers` (dict), `done`, `created_at`/`updated_at` (ISO), `drop_off_step`, `record_id` (the Session row's own Airtable id), `last_uploaded_file`, `last_tool_result`, `current_lead_record_id`, `active_lead_candidate` (TTL 1800s), `last_lead_candidate_batch`, `pending_lead_preview` (TTL 1800s), `last_prompted_contract` (TTL 600s), `lead_draft` (TTL 1800s), `commercial_completion`, `deal_enrichment_offer`, `lead_deal_link`.

**Airtable field mapping** (`_sync_to_db`, L703-799; `SessionsFields`/`SF` in `airtable_schema.py` L1535-1554): `SENDER_ID`, `CONTEXT_TYPE`, `CHANNEL`, `STATE_JSON` (a single JSON blob field holding the *entire* dict above, minus a small non-serialized subset — `record_id` itself, `context_type`, `channel`, timestamps go to their own columns; everything else nests inside `STATE_JSON`), `UPDATED_AT`, `CREATED_AT`, `SESSION_ID` (deterministic `tenant:channel:sender` composite key, L48-58 — was defined in schema but never written until BUG-SESSION-DUP fix), plus optional link fields `LINKED_LEAD`/`LINKED_DECISION`/`LINKED_MEDIA_FILE` populated conditionally. **No dedicated columns exist per draft-field** — it's all opaque JSON in `STATE_JSON`, so nothing is independently queryable/filterable at the Airtable level for e.g. "all pending lead drafts."

**Query/retrieval API**: `get(sender, channel="")` (L275-293, RAM then DB fallback), `get_or_create(sender, domain, channel)` (L295-351). Keyed by **`(tenant, channel, sender)`**, not by any draft/record id — `_canonical_session_key()` = `f"{tenant_id}:{channel}:{sender}"` (L48-58, hardcoded `tenant_id="boss_hq"` today — single-tenant placeholder, L39-45: *"documented, intentional placeholder... never read as evidence multi-tenancy is active"*). There is **no lookup by draft_id** — a draft only exists as a nested key inside the one session row for that sender+channel.

**Concurrency**: `self._create_lock = threading.Lock()` (L238, comment L235-237: *"get_or_create is GET-then-POST — without a lock, two concurrent calls for the same sender can both miss RAM+DB and both create+sync a session, producing duplicate Airtable rows"*) — guards only the create path (double-checked locking, L340-351), not general read/write of session fields. Individual field setters (`set_lead_draft`, `set_pending_lead_preview`, etc.) are **not** lock-protected — a race between two concurrent turns for the same sender+channel could clobber each other's last-write-wins state (no optimistic concurrency/version field on the session dict itself). RAM cache is process-local (`OrderedDict` in a Python object) — **no cross-process/cross-worker locking** at all; only the DB layer's `_find_best_session_in_db`/duplicate-detection (L863-896, logs `SESSION_DUPLICATE_DETECTED` but never merges/dedupes automatically) is a partial safety net against concurrent creates from different workers.

**Multiple simultaneous sessions per user**: **No** — one session per `(tenant, channel, sender)` triple is the enforced model (`get_or_create`'s cross-channel-collision check, L303-339, explicitly refuses to reuse a session created under a different channel, logging `SESSION_CROSS_CHANNEL_COLLISION`). A user can't have two concurrent drafts/previews on the same channel — `lead_draft`, `pending_lead_preview`, `active_lead_candidate` are each a **single nested key**, so starting a second one overwrites the first with no queue/stack.

**Versioning**: none — every write is a full overwrite of `STATE_JSON` for that row (`_sync_to_db` always serializes the *whole* state dict); no optimistic locking, no revision counter, no conflict detection between two writers touching different sub-keys concurrently (last full-state-write wins).

**TTL/expiry**: enforced only at **read time**, per-key, hand-coded in each getter (not a generic mechanism): `active_lead_candidate` >1800s (L464-480, expiry clear synced to DB per the fix noted at L466-468), `pending_lead_preview` >1800s (L538-553, syncs the clear), `last_prompted_contract` 600s (referenced L1056-1057), `lead_draft` also 1800s per comment L565-568/1056. There is no background sweep/cron — an expired key only gets cleared the next time its specific getter is called for that sender.

**Duplicate-record handling**: `_select_canonical_session_record()` (L114-138) picks the most-recently-`Updated At` row when the Sender-ID(+channel) lookup formula returns more than one Airtable row for the same sender — logged via `_log_duplicate_detected` (`SESSION_DUPLICATE_DETECTED`, cross_channel flag) but **never auto-merged or cleaned up**; stale duplicate rows persist in Airtable until a manual, human-confirmed cleanup (explicitly stated not to be this code's job, L854-855).

**Cleanup semantics**: `_evict_if_needed()` (L998-1009) — pure LRU eviction from the RAM `OrderedDict` when >1000 entries; evicted-but-not-done sessions get one final `_sync_to_db` (marking `drop_off_step`) before falling out of RAM — Airtable row is never deleted, only marked (`_delete_from_db`, L973-994, sets `done=True, deleted=True` inside `STATE_JSON` — no real Airtable delete, no `Status`/`Deleted` column exists on the table per BUG-098's finding, L122-123).

**Concurrency/TTL/payload-size caveats relevant to a future BusinessDraft reuse decision**:
- Single-row-per-`STATE_JSON`-blob design means arbitrarily many draft-like sub-objects share one Airtable long-text field with no independent size accounting — nothing in this file guards against `STATE_JSON` growing unbounded as more state keys accumulate (already 16 keys today, more added over time per the file's own change-history comments, e.g. DIAMOND REMEDIATION D1 lines).
- No per-draft locking — concurrent turns on the same chat could race; the only lock covers first-creation, not subsequent field mutations.
- One-session-per-`(tenant,channel,sender)` means a future BusinessDraft framework wanting **multiple concurrent drafts of different entity types** for the same user already works today only because each draft type gets its OWN top-level dict key (`lead_draft` vs `deal_enrichment_offer` vs `lead_deal_link`) — i.e. the existing pattern is "one slot per draft *kind*," not "N slots for N drafts of any kind." A generic BusinessDraft abstraction that wants arbitrary-cardinality drafts (e.g. multiple simultaneous Lead drafts) is **not directly supported** by this schema without adding an indexed/keyed sub-structure.
