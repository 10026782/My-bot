## 2. CREATE vs UPDATE

**No update writer exists for any commercial entity.** Grep `^def ` in `commercial_crm.py` has zero `update_deal`/`update_payment_term`/`update_payment`/`update_charge`. `commercial_completion.py`'s own `CommercialCompletionWriter` is CREATE-only (`complete_payload()` raises if fields are missing; no "existing record" path). The only update-capable path for the commercial model is the generic `airtable_update` dispatcher case — and per `commercial_crm.py`'s module docstring ("S2B adds only universal Organization resolution, Charge creation, and Charge-required actual-movement Payment creation") and the S2B evidence doc (`docs/evidence/COMMERCIAL_S2B_MUTATION_PRIMITIVES_20260903.md` L24, L85): "generic updates to Charges and Organizations fail closed because no update primitive was approved." Contact is the one exception: `crm.update_contact(record_id, fields, source="contact_gate")` (`crm.py` L342) is live and wired — `tools/dispatcher.py` L887 routes generic `airtable_update` on the Contacts table through it.

## 3. DIAMOND PATH mechanism (`commercial_completion.py` + `commercial_completion_routing.py`)

Core state (`commercial_completion.py`):
- `CommercialCompletionWriter` (L671) — pure per-entity field-completion state machine (`resolved_values`, `missing_fields`, `next_field`, `apply_answer`, `complete_payload`).
- `_CompletionFrame` (L788) — `{writer, return_field}` pair.
- `ContinuationRef` (L798) — typed, versioned pointer `{session_key, channel, nested_entity, return_field, nonce}` stored on the queued ActionContract itself (not a copy of the session — session_store stays the single source of truth). `session_key` is the raw chat_id, never the composite session-store key.
- `CompletionSession` (L897) — an immutable stack of frames: `.start()`, `.begin_nested(target_entity, return_field=...)` (only into a `LINK` field, L901-ish), `.resume_parent(canonical_record_id)` (pops nested frame, folds record id into parent's `return_field`), `.abandon_nested()` (pops without folding, for reject/orphan cleanup).

Orchestration (`commercial_completion_routing.py`):
- `SUPPORTED_COMPLETION_ENTITIES` (L34) = `{deal, payment_term, organization, charge, charge_from_term, payment}` — **"contact" is deliberately excluded** (L38 comment: nested-only, entered exclusively via `begin_nested()`, never `router.start("contact", ...)`).
- `MUTATION_TOOLS` (L46) maps entity→tool name, incl. `"contact": "crm_find_or_create_contact"`.
- `CommercialCompletionRouter.answer_human()` (L465) is where the UX branches: when a LINK field's free-text answer resolves to zero candidates (`resolution.status == "create"`), it marks the PARENT session with `_ux_pending_nested_create` (field, nested_entity, candidate_name, prompt) and returns `CLARIFY` with choices `("כן","לא")` — `begin_nested()` is deliberately NOT called yet. On the next turn, if the reply is in `_CREATE_CONFIRM_WORDS`, `begin_nested()` is called (constructing a nested Contact/Organization `CommercialCompletionWriter` pre-seeded with the candidate name); "לא" drops the offer and re-asks the parent field.
- `CommercialCompletionRouter._inspect()` (L~610): when a nested frame (`len(session.frames) > 1`) reaches `complete_payload()`, it mints a fresh nonce (`secrets.token_hex(8)`), embeds it in the nested writer's `current_values["_pending_approval_nonce"]`, and passes a `continuation_hint` dict `{nested_entity, return_field, nonce}` as an optional 3rd positional arg to the injected `queue()` callback.
- `CommercialCompletionRouter.resume_nested()` (L406): reloads the parked session, verifies `(target_entity, return_field, nonce)` correlation exactly, then either resumes (folds `canonical_record_id` into parent and continues inspection), or returns `"mismatch"` (a different/no session parked — fail closed, don't touch session_store) or `"corrupted"` (correlated but no usable record id — caller must `.abandon_nested()`).

Execution-side wiring in `app.py`: `_queue_approval_detailed()`/`_queue_approval_detailed_impl()` (L1743/L1951) build the `ContinuationRef` (L1969, `ContinuationRef.for_commercial_completion`) and attach it to the `ActionContract` (L2033, L2242). On approval callback, `app.py` L3504-3529 reads the parked state from `session_store.lead_sessions.get_commercial_completion()`, builds a fresh `CommercialCompletionRouter`, and calls `router.resume_nested(...)`.

**Actual UX shape** (from `test_diamond_path_approval_continuation.py` L45-64 and `test_bug_diamond_contact_approval_and_search.py` header, both real production transcripts): user is mid-Deal-completion → answers counterparty name ("יאיר ממן") → no match → bot replies "ליצור איש קשר חדש?" (choices כן/לא) → user types "כן" → bot asks next missing Contact field ("מה מספר הטלפון?") → user answers → nested Contact completion is complete → queued to the OWNER's Telegram inline-keyboard approval (regardless of which channel the parent completion is on) → owner approves → `crm_find_or_create_contact` executes → `resume_nested()` folds the new Contact record id into the Deal's `counterparty_contact` → Deal completion continues asking its next missing field (or queues the Deal create itself).

Two real production bugs on this exact path (both closed, see `test_bug_diamond_contact_approval_and_search.py`): (1) `action_validator._REQUIRED`/`_SENSITIVE_TOOLS` initially missing `crm_find_or_create_contact`, causing "Unknown tool blocked" even though it was correctly registered elsewhere; (2) `lookup_human_reference` never sent the query to Airtable server-side, only scanned the first 7 records client-side.

## 4. `commercial_completion.py`'s writer vs `commercial_completion_routing.py`'s router — division of ownership

Per `docs/governance/WRITER_AUTHORITY_REGISTRY.md` and the module docstrings: `commercial_completion.py` owns pure, entity-agnostic field-contract state (no I/O, no session_store/chat_id/channel knowledge — explicit in `resume_nested`'s own docstring, L406-419 of `routing.py`). `commercial_completion_routing.py` is "deliberately an adapter" (L1 docstring) that owns deterministic recognition/orchestration and hands a complete validated payload to the caller-supplied `queue()` boundary — it does not import a generic mutation helper or ActionGateway implementation itself. One narrow, explicitly-flagged exception: `_apply_charge_from_term_context()` (L178) does a read-only Airtable read of the live Payment Term to resolve a Conditional field requirement (BUG-CHARGE-TERM-BYPASS), never a write.

## Notes for the design doc

- No commercial entity has an UPDATE writer at all — a real gap BusinessDraft will need to address if it's meant to generalize beyond create.
- DIAMOND's nested-completion mechanism is entity-generic in principle (`begin_nested()` takes any `target_entity` string) but only Contact and Organization are actually wired for the "no match → offer to create" UX (`_NESTED_CREATE_ENTITIES` in `routing.py` L67); Deal-needs-a-Deal or Charge-needs-a-Term nesting isn't offered today, only referenced by ID.
- Organization is barely a schema (one field) but already has a full find-or-create writer and DIAMOND nested-create wiring — worth flagging as a scope mismatch if BusinessDraft treats "entity richness" and "writer/UX maturity" as coupled.
