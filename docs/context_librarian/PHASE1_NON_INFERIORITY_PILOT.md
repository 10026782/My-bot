# Phase 1 Agent Workflow Non-Inferiority Pilot

This document defines the Phase 1 comparison. It does not claim that the pilot
has passed. Quality results must be recorded before reading-savings results.

## Fixed comparison

Run every task in separate, uncontaminated contexts against the same commit,
task text, change boundaries, tests, architecture invariants, and static checks.

| Track | Initial context |
| --- | --- |
| Baseline | Repository instructions and the normal broad-context workflow |
| Librarian | Canonical bootstrap, explicit profile selection, and bundle |

The five pilot tasks are:

1. Repeated approval returns the wrong message.
2. Dispatcher reports success without execution evidence.
3. An explicit request routes to the wrong handler.
4. Business Outcome maps to the wrong reasoning state.
5. A completion claim conflicts with available evidence.

Codex and Claude Code must independently run the Librarian track. Store the raw
suggestion output, selected profile, commit, bundle SHA-256, bundle size, and
workflow-gate status. Identical inputs must produce identical bundles.

## Independent Authority Gold Set

Before each solution, an independent reviewer with full repository access must
define the material code, definitions, imports, callers, callees, adapters,
schemas, flags, persistence readers/writers, tests, renderers, approval paths,
evidence consumers, architecture contracts, authority documents, and production
evidence. The reviewer must not derive this set from the bundle.

Compare every source actually opened with this gold set. For a shared identifier
or a change spanning layers, attach a Cross-Layer Impact Matrix containing:
layer, owner, input, output, source of truth, callers, consumers, approval
boundary, evidence boundary, user-facing effect, tests, and duplicate-ownership
risk.

## Per-run record

Record these fields for both tracks:

- agent, task, track, commit, task text, and selected profile where applicable;
- tests, architecture gates, static checks, and functional defects;
- gold-set misses, cross-file/layer misses, and architecture defects by severity;
- architecture corrections, material context corrections, and first-pass result;
- every context expansion: source, reason, discovery path, necessity, recurrence;
- files opened and source bytes/tokens read.

An independent full-repository review should be blind to the track where
practical. It must look for duplicate ownership, parallel sources of truth,
approval bypass, hidden routing or reasoning changes, claim/evidence mismatch,
planning treated as current main, missing callers/consumers/schemas/flags, work
in the wrong layer, and unsupported production claims.

## Evaluation order and acceptance

Evaluate tests and architecture gates first, followed by functional defects,
gold-set misses, cross-file/layer misses, architecture defects, review
corrections, context corrections, first-pass acceptance, and context expansions.
Only after every quality gate passes may the report reveal files, bytes, context
size, or estimated token savings.

Acceptance requires identical Codex/Claude bundles for the same explicit
profile and commit; no silent selection; zero material authority misses; zero
Critical/High architecture defects; baseline-equivalent tests and architecture
gates; no increase in functional defects or material corrections; every
material external dependency recorded; zero excluded-layer leakage; independent
review of every solution; writing quality, accuracy, and usefulness no lower
than Baseline; and no runtime or production change.

Any quality failure is a regression regardless of reading savings. Five tasks
permit only a cautious manual rollout, not a general statistical quality claim.

## Results

### 2026-07-27 bootstrap preflight on `23d6a47`

Codex ran all five task descriptions twice with explicit profiles. Suggestions
and bundles were deterministic within each task. The real workflow gates were:

| Task | Explicit profile | Gate | Reason |
| --- | --- | --- | --- |
| Repeated approval message | `approval_ux` | STOP | stale approvals, Turn Coordinator, and F52 nodes |
| Dispatcher success without evidence | `tool_execution` | STOP | stale approvals and RP5 nodes |
| Wrong handler routing | `turn_coordinator_routing` | STOP | stale approvals and Turn Coordinator nodes |
| Wrong Business Outcome reasoning state | `core_reasoning_change` | PROCEED | none |
| Claim/evidence conflict | `rp5_evidence_mismatch` | STOP | stale RP5 and F52 nodes |

The four stopped tasks were not planned or implemented. Their bundles remained
available and identified the changed paths requiring re-verification. No
reading-savings result is reported for them.

The reproducible Core Reasoning input was generated by implementation commit
`3ab4ac31077e8d5e511f141258b7cda10b000cba` with the exact task text:

```text
Business Outcome maps to the wrong reasoning state.
```

Raw suggestion output:

```text
core_reasoning_change score=2 matched=business outcome, reasoning
approval_ux score=0 matched=none
cross_layer_architecture score=0 matched=none
rp5_evidence_mismatch score=0 matched=none
tool_execution score=0 matched=none
turn_coordinator_routing score=0 matched=none
ux_f52_message score=0 matched=none
Selection status: unique_suggestion; top_score=2; candidates=core_reasoning_change; automatic_selection=false
Suggestion only: pass an explicit --task-type to build.
```

Explicit selection: `Selected profile: core_reasoning_change`. Two builds used
the repository virtual-environment interpreter with:

```text
python -m tools.context_librarian build --task-type core_reasoning_change --query "Business Outcome maps to the wrong reasoning state." --output <artifact.md>
```

Each canonical LF/UTF-8 artifact was 5,158 bytes. Both had SHA-256
`b1cf9ef0335f4201867b4f87d043581e3152f9281a09607d22c5ad8dd7dde8cc`.
The gate was `PROCEED` with no reasons, zero stale nodes, 100% mandatory
authority, `production_claim: false`, `verified_production_evidence: none`, zero
qualifying production evidence, zero unresolved conflicts, and zero
excluded-layer leakage.

The Core Reasoning task received one isolated Baseline audit and one isolated
Codex Librarian audit. Both found that Lead Business Outcome semantics are
compressed into generic Decision phases and identified `meeting_scheduled` and
other intermediate/high-signal outcomes as architectural risks. The Librarian
run opened its cited sources and recorded adapter, shared-orchestrator, schema,
flag, writer, event, and consumer context expansions.

This is not a completed non-inferiority result: no solution was implemented;
the Authority Gold Set was not fixed before the runs; no blind solution review
was possible; and the quality comparison is therefore preliminary. Files-read,
source-volume, context-size, and savings figures remain intentionally withheld.

Claude Code execution was attempted in read-only plan mode but blocked by the
environment's egress policy because it would send repository instructions and
bundle content to an external service without explicit authorization. Therefore
Codex/Claude bundle equality and the two-agent acceptance condition remain
unproven.

The full repository test runner required per-file execution because several
legacy script-style tests call `sys.exit()` during pytest collection. Of 175
test files, 169 passed and 6 failed. The same six files failed in a clean
detached `origin/main` worktree, so they are baseline failures rather than
branch regressions. All Context Librarian tests passed.

Phase 1 acceptance is not established. Do not bypass a real STOP merely to
complete the pilot or expose savings metrics.
